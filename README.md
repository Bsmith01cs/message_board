# message_board

CSC 4360 Homework 02 — a Flutter message board using Firebase Authentication
and Cloud Firestore. Android is the target platform.

## Overview

Users register or sign in with email and password, which creates a private
profile document in Firestore. A complete profile is required before the board
is reachable. On the board, any signed-in user can read every message in real
time, and each user can post, edit, and delete their own messages.

- **Authentication** — email/password registration, sign-in, and sign-out,
  handled entirely by `AuthService`. `AuthGate` watches
  `authStateChanges()` and swaps between the login flow and the signed-in
  destination; no screen navigates manually after signing in.
- **Profiles** — `ProfileGate` listens to `users/{uid}` and keeps the board
  unreachable until the five required fields are present, offering a
  completion form when they are not.
- **Messages** — `BoardService` owns all four CRUD operations against
  `messages/{msgId}`. The board renders a `snapshots()` stream, so new,
  edited, and deleted messages appear without any refresh action. Edit and
  Delete are shown only on a user's own messages, and the security rules
  enforce that independently.

## Setup

1. Install Flutter (Dart SDK ^3.13.4) and the Android SDK.
2. From this directory, fetch dependencies:

   ```
   flutter pub get
   ```

3. Firebase is already configured for the project `intro-firebase-2ee9f`:
   `lib/firebase_options.dart` and `android/app/google-services.json` are
   committed and contain only public client configuration. To point the app at
   a different Firebase project, re-run `flutterfire configure`.
4. In the Firebase console, Email/Password sign-in must be enabled and the
   rules in `firestore.rules` must be deployed (see below).

```
flutter run
```

An Android emulator or device must be connected (`flutter devices`).

## Firestore data model

### Collection: `users/{uid}`

| Field | Type | Written by |
| --- | --- | --- |
| `uid` | String | `UserRecordService.saveProfile` (value taken from Firebase Auth) |
| `firstName` | String | `RegisterScreen`, or `CompleteProfileScreen` on retry |
| `lastName` | String | `RegisterScreen`, or `CompleteProfileScreen` on retry |
| `role` | String | `UserRecordService`, defaulting to `member` |
| `registrationDateTime` | Timestamp | `UserRecordService`, via `FieldValue.serverTimestamp()` |

The document ID is always the Firebase Auth UID. `role` is descriptive data
only — it never grants privileges in the app.

### Collection: `messages/{msgId}`

| Field | Type | Written by |
| --- | --- | --- |
| `text` | String | `BoardService.postMessage` / `editMessage` |
| `authorUid` | String | `BoardService.postMessage`, from the signed-in Auth user |
| `authorName` | String | `BoardService.postMessage`, built from the author's profile |
| `createdAt` | Timestamp | `BoardService.postMessage`, via `FieldValue.serverTimestamp()` |
| `editedAt` | Timestamp or null | `BoardService.editMessage`, via `FieldValue.serverTimestamp()` |

The document ID is generated by Firestore and is kept on `BoardMessage.id` so
a message can be edited or deleted later.

## Design notes

**Why profiles are separate from messages.** A profile is one record per
person that changes rarely; messages are many records that are read as a
single ordered list. Keeping them apart means a name change touches one
document instead of every message, and the board can be loaded without
reading anyone's profile. `authorName` is copied onto each message so the
board needs no extra lookups to display who wrote what.

**Why server timestamps.** `FieldValue.serverTimestamp()` is filled in by
Firebase, not by the phone. Device clocks can be wrong or deliberately
changed, so a client-supplied time would make the ordering of the board
unreliable. The same reasoning applies to `registrationDateTime`.

**Why messages use `snapshots()`.** `BoardService.messageBoard()` returns a
stream from `snapshots()`, so the board updates itself as soon as anyone
posts, edits, or deletes — no refresh button and no polling.

**How ownership is enforced.** `BoardService` always takes `authorUid` from
`AuthService.currentUser`, never from the caller, and `editMessage` writes
only `text` and `editedAt`, so ownership and creation time cannot be
rewritten. `BoardMessage.isOwnedBy` exists only to decide what the UI offers.
Hiding a button is not security: Firestore Security Rules are the final
authority and must restrict writes to `request.auth.uid == resource.data.authorUid`.

## Firestore authorization model

`firestore.rules` is the authorization boundary. The UI hides Edit and Delete
on other people's messages, but hiding a button is not security — every rule
below is enforced by Firestore itself. The rules use version 2 and are
default-deny: a path is reachable only where a rule grants it.

**Private user records.** `users/{uid}` is readable only by the user whose
Auth UID matches the document ID. Listing the `users` collection is denied, so
nobody can enumerate classmates. A user may create their own profile and may
complete or repair an incomplete one, but the `uid` field must match the
document, names must be non-empty strings, `role` may only be introduced as
`member` and can never change afterwards, and an existing
`registrationDateTime` can never be rewritten. Profile deletion is denied.

**Message ownership.** Any signed-in user may read the board; signed-out users
may not read it at all. A message can only be created with
`authorUid == request.auth.uid`, so ownership cannot be forged, and `createdAt`
must be the server timestamp. Only the original author may update or delete a
message, an update may affect only `text` and `editedAt`, and `authorUid`,
`authorName` and `createdAt` are immutable.

## Local security testing

The rules are tested against the Firestore emulator on the isolated demo
project `demo-message-board-hw02`, configured in `.firebaserc`. No test
touches the live project.

Requires Java 21 or newer (`firebase-tools` refuses older JDKs):

```
cd firestore-tests && npm install
cd ..
JAVA_HOME=/opt/homebrew/opt/openjdk@25 \
  firebase emulators:exec --only firestore \
  --project demo-message-board-hw02 "cd firestore-tests && npm test"
```

Last run: **42 rules tests, 42 passing, 0 failing**, against the emulator.
The Flutter suite is **108 passing** with `flutter analyze` clean.

**Production deployment is pending.** These rules have never been deployed.
The Firebase project `intro-firebase-2ee9f` is shared with other coursework,
and `firebase deploy` replaces an entire ruleset, so the live rules must be
read and merged before anything is deployed.

## Project layout

```
lib/
  main.dart                      splash screen and Firebase initialization
  models/board_message.dart      message model and document builders
  screens/board_screen.dart      the message board: live list and composer
  screens/login_screen.dart
  screens/register_screen.dart
  services/auth_service.dart     all Firebase Authentication calls
  services/board_service.dart    all Firestore message operations
  services/user_record_service.dart  all Firestore users/{uid} operations
  widgets/auth_flow.dart         login / register switching
  widgets/auth_gate.dart         signed-in vs signed-out routing
  widgets/profile_gate.dart      requires a complete profile before the board
```
